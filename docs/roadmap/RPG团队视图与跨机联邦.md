## 一、核心架构裁决（防 RPG 变成第二个世界）

用户裁决：**需要 L2 编排**——任务引擎 = 既有编排，不新造。由此推出四条落地裁决：

1. **游戏态两分：观察态全派生，行动态落 RPG 域**。观察态（角色状态机 =
   `deriveSessionStatus` 映射：running→工作中、compacting→蓄力、failed→受伤、
   idle→空闲、terminated→离场；XP / 等级 / 成就 = `hook_events` 只读统计）零第二
   数据源；行动态（修炼记录、技巧评分、装扮偏好）是**游戏自己的事实**，落 RPG 域表
   ——判据见第十章「这是游戏的事实还是会话的事实」。
2. **任务 = L2 编排 run**。weaveRPG.md 的任务系统（日常 / 主线 / Boss / 迭代）不新造
   引擎：编排图就是任务的依赖与流程，run 状态就是任务状态，RPG 视图是编排运行态的
   游戏化渲染。L1 扩展点（批 2b 后）提供任务过程中的事件反馈（角色回合结束 →
   任务进度拍点）。
3. **角色 = 类，化身 = 实例**（2026-10-26 用户裁决：分身中角色是一类，同一角色在
   不同会话中 = 同一角色的不同实例，**同一角色、各负责不同模块**）。角色仓库是
   一个 weave 项目（身份、六维、技能、装备库都是角色级 = 项目档）；化身 = 该项目
   里的一个会话实例（武器 = 模型、内力 = 上下文长度、状态机、**负责模块**都是
   化身级 = 会话级）——**RPG 对象层级与 weave 作用域层级天然同构**（角色级 =
   项目档、化身级 = 会话、门派基础 = user 档全局 skill 继承）。**v1 即支持多化身**
   （同角色多实例并行，模块分工 = 创建实例时的声明，协调者派单或用户指定）。
   角色项目在 `projects.meta` 带分组标记（字段已有）——dashboard 按组折叠、
   RPG 视图展开，两视图共享同一份项目注册表。
4. **协调者 = 招聘人员**（2026-10-26 用户裁决）。职责链 = **创建角色 → 发现技能 /
   探索技能 / 发现插件 → 给角色组装模块 → 派任务**。发现与探索依赖 AI 与 web
   search——这是**内置 harness 能力的一部分**（宿主会话自带，如 claude 的
   WebSearch），weave 不自建搜索；发现结果（候选 skill / 插件清单 + 适配评估）先落
   协调者仓库 `state/` 作工作底稿（可追溯、可批阅），组装走修炼 / 换装动词。协调者
   仓库是 weave 内置资产（对齐内置市场仓先例）；协调者会话由 L2 编排驱动（autoFire
   自然回合 + 任务指示投递），它用 weave MCP 工具（weave-projects / weave-sessions）
   执行建队与调度——**协调者是 MCP 生态的第一个重度消费者**，RPG 计划与 MCP 计划
   在此交汇。
5. **游戏操作 = 服务端语义门面，门面下恒是既有 API**（用户裁决 2026-10-25）。游戏
   视图的一切写操作先抽象成游戏动词（修炼 / 组队 / 出征…），门面层把动词翻译成
   既有 API 调用并落游戏事实——**零新写实现**：业务裁决（安装校验、投递层序、编排
   触发）全部仍在既有 API，门面只做映射 + 组合 + 游戏事实记录，永不自带裁决。
6. **RPG 代码与既有代码零耦合，经适配层双向交互**（用户裁决 2026-10-25）。RPG 域
   是独立模块（server 侧 `src/rpg/` 独立域 + web 侧 `web/src/rpg/`），**依赖方向
   单向**：`rpg → 适配层 → 既有域`；既有域永不 import RPG（唯一例外 = daemon
   装配点单点挂载，既有惯例）。适配层 = 接口 + 纯函数组装（不新增抽象类，对齐全仓
   红线；形态同 `PluginSurface` / 决策内核先例）：**读侧**给观察态派生素材（会话
   状态、事件统计、工具安装态），**写侧**即动词门面（5.2）。RPG 可整体启停
   （settings 闸，缺省不装 = 零开销），未来可整体拆包甚至独立发布而不动既有域。
7. **化身运行时 = 双通道：ACP-lite 与终端共生分管两个场景**（2026-10-28 裁决，据
   Codeg / claude-agent-acp 源码实测）。**RPG 化身与编排目标会话走 ACP-lite**（weave
   spawn 适配器起 daemon 子进程——游戏视图即视图、不占用户终端 pane；`session/prompt`
   → `TurnComplete` 即回执，回执闸天然满足；`session/fork` 原生支撑分身术；ACP 流自带
   live diff / tool call，游戏视图素材更富）；**用户自己的终端会话走既有终端共生**
   （hook 采集 + 击键，ACP 够不着的场景，见定位稿「ACP 覆盖边界」）。**角色属性与协议
   无关**：角色 = 独立 project，skill / MCP 是 agent 启动时自己读项目文件（`.claude/
   skills`、`.mcp.json`），ACP spawn 传 `working_dir` = 角色仓库即全部生效——裁决 3
   的对象层级原样成立。**三个整合点**：① 事件归一——ACP `session/update` 流翻成
   `HARNESS_EVENTS` canonical 词表入库（autoFire / turnOpen / 编排推进照旧）；待实测
   红利 = claude-agent-acp 基于 Agent SDK，SDK 会话可能仍触发项目 hooks，若属实采集面
   零改动、ACP 只管投递；② 投递通道——`MessageDeliverer` 加 ACP 层，层序按会话运行时
   分流（ACP 会话 prompt 即达，终端会话层序不动）；③ 混合图——DAG 节点双运行时，
   事件归一后引擎无感。**steer 编排 v1 不用**（保持回合边界模型），留用户手动插话。
   **落位**：C3（RPG-1）v1 化身仍走既有终端 spawn（零新依赖、验收不变），ACP-lite
   作独立工作项（ACP-1）落地后化身默认运行时切换为 ACP、两通道并存。

## 三、角色插件与角色仓库（provisioning）

**角色 = 可复用的 weave 插件**（2026-10-26 用户裁决）。两层分离：

- **角色插件（可复用定义）**：weave 插件形态，市场分发——内含人设（CLAUDE.md 素材）、
  六维基线声明、默认 skill / MCP / 插件清单（该型默认装备）。基础七型 = weave 内置
  角色插件；用户与协调者开发的角色插件经市场安装。**同一角色插件可实例化到多个
  团队**（可复用的本义）。
- **角色仓库（实例化产物）**：从角色插件实例化出的 weave 项目——`weave init`（采集 /
  hook 面）+ 装角色插件 + 起会话。默认根 `<dataRoot>/data/rpg/roles/<role>/`（对齐
  市场副本先例，**迁移整档带走**）；自定义根 = settings 键（`rpg.rolesRoot`），搬迁走
  `ensureDataLayout` 纪律（只 rename 从不删、幂等、活 daemon 占用则整个不动）。
  全局 user 档 skill 既有机制天然继承。
- **复用角色** = 已注册项目直接入队（不重建）；角色退役 = 项目归档（既有
  `archived_at`），不删仓库。
- **插件系统 = 统一分发载体**：角色插件、皮肤包插件都是 weave 插件的类型（manifest
  声明类型），注册制扫描统一适用（装到即注册）；插件机制改动走三件套硬约束。

## 四、协调者仓库

内置资产（对齐内置市场仓先例），目录结构：

```
coordinator/
  teams/        # 团队声明：角色项目集 + 编排图引用 + 团队目标
  roles/        # 内置角色插件（基础七型；用户/协调者开发的角色插件走市场）
  playbooks/    # 任务剧本：Boss/副本的编排图模板（含 when/condition 边闸）
  state/        # 协调者会话的运行素材（任务指示、发现工作底稿、进度笔记）
```

- **整体迁移到自定义路径**：settings 键 + `ensureDataLayout` 式搬迁（同上纪律）。
- **协调者 skill**（2026-10-26 用户裁决）：内容 = 整个 weave 的操作描述（怎么建项目 /
  init / 起会话 / 触发编排 / 投递——即 MCP 工具的使用手册），**落内置 weave 插件**
  （init 装的插件面，所有 weave 项目天然可用）；协调者仓库不再自带这份知识。
- **协调者角色 = RPG 中用户创建的唯一角色**（上帝视角，singleton）：它也是一个
  项目 + 会话，但全队仅此一个、不参与六维与任务分配——它看全图、派全单。
- **协调者会话**：常驻、由 L2 编排驱动——「创建团队 / 复用角色 / 派任务」都是投递给
  它的 prompt；它经 MCP 工具执行（建项目、init、起会话、触发编排）。协调者自身的
  回合是诱导回合（批 2a 登记机制覆盖），不会自触发风暴。
- **任务指示入口（2026-10-26 定）**：协调者就是个会话——**直接在它的对话面板里说**
  就是入口；RPG 视图的「点将 / 下达任务」按钮 = 同一通道（`MessageDeliverer.send`）
  的游戏动词皮肤，不是第二条通道。
- **文件格式（简版占位，2026-10-26 起草）**：

```yaml
# teams/<name>.yaml —— 团队声明
name: 前端小队
goal: 完成 XX 模块
roles:
  - role: frontend-dev            # 角色仓库名（项目 key）
    instances:
      - module: web/src/ui        # 化身分工：同一角色多实例各负责一个模块
orchestration: playbook://boss-landing
```

```yaml
# playbooks/<name>.yaml —— 任务剧本（编排图模板）
name: Boss·落地页
kind: boss                       # 日常 | 主线 | 团队 | boss | 迭代
difficulty: 7                    # 1-10（任务属性 = 标注，不是运行时）
risk: 3
reward: { xp: 500 }
graph:                           # 节点用 r:<role> 占位引用角色
  nodes:
    - { id: r:frontend-dev, kind: session, role: frontend-dev, module: web/src/ui }
  edges:
    - { from: t:start, to: r:frontend-dev, text: "实现 {upstream}" }
```

  **playbook 参数化机制（2026-10-29 用户裁决：A——文件层实例化）**：节点 id 用
  `r:<role>` 占位引用角色，实例化时按 `module` 匹配绑定到具体化身（无 module = 主
  化身）——**模板 → 编排的转换是纯函数（占位替换 + `create_orchestration`），落在
  协调者侧（RPG 适配层 / 动词门面），编排域不知道模板的存在**：不扩编排表、不加
  「模板实例化」概念、编排域零改动（零耦合红线自动满足）。任务属性（difficulty /
  risk / reward）随 playbook 文件走 = 模板元数据，orchestrations 表不加字段
  （11.4#3 一并消掉）。协调者 skill 写清「选 playbook → 渲染 → 建编排」的调用序列。

  **互馈环模式（2026-10-29 设计注，dev↔test 实例导出）**：单张编排图静态拒环
  （`validateOrchestration` 既有裁决），**互馈 = 一剧本渲染多张编排交叉自然回合**——
  编排 A（dev 入口 → test）+ 编排 B（test 入口 → dev，边闸 `when`/`condition` 做
  终止：全绿时 B 边被拦、环自然停）。环的驱动是数据（自然回合），无需额外提示词。
  ⇒ playbook 格式须支持**多图**（`graphs: [...]` 渲染成编排集），见 11.3#16。

  **两条反馈通道各司其职（2026-10-29 补）**：claude↔claude 有原生回复面（中继只送
  第一棒、身份 `weave` 一次性进程——有用回复 = 目标用 SendMessage 直呼源会话，
  `prompt.ts` 编排域故意不加单向注记），适合载 **ad-hoc 澄清**（多轮问答不过编排）；
  **工作流节拍（正式测试报告→修复指令）恒走编排边**——终止闸 + run 日志可观测
  （用户可观测性裁决划线）+ 跨 harness 通用（codex 无 SendMessage / 回复面，
  `PromptRelaySpec` 非 claude 恒 null）。两通道共存不冲突。

## 五、游戏视图与游戏语义层（web + 动词门面）

### 5.1 游戏视图（web）

- **入口**：dashboard 右上角视图切换（仪表盘 ↔ RPG），**路由化**（位置即 URL，
  `parseRoute` 单向落下）；卡片内部视图态不进 URL 照旧。
- **场景系统**（用户补充 2026-10-26）：RPG 视图 = 场景集 + 场景切换，v1 四场景——
  1. **办公区俯视**（MVP 基底）：团队地图——角色卡（像素立绘 + 状态映射动画）+
     任务栏（编排 run 的游戏化呈现）+ 点击角色进**既有**会话详情（不复制对话面）。
  2. **教室（大屏黑板）**：黑板 = 团队简报位——今日任务板（编排 runs 排程）、团队
     点名（角色状态总览）、成长榜（XP/等级派生）。粉笔字/板擦痕迹为 CSS 效果。
  3. **会议室（大屏）**：大屏 = 展示与批阅位——**review 批阅的 UI 落点**（改动汇总
     diff 投屏 + 「同意/驳回」动词，定位稿① 闭环在此完成）、任务复盘（run 日志
     回放）、指标大屏（仪表盘速率图的游戏化换皮）。
  4. **武林大会（竞技场，2026-10-26 用户裁决进 v1）**：江湖主题——六维雷达对决
     （角色两两对比）、排行榜（XP / 等级 / 成就的竞技化呈现）、兵器谱（武器品阶
     榜）。**只做派生呈现，不做对战模拟**（模拟 = 第二游戏引擎，红线）。
- **大屏 = 协调中枢**（2026-10-26 用户裁决定纲）：武林大会 / 教室 / 会议室只是场景
  （皮肤），**根本目的 = 多角色工作流程的编排**；三场景的共同点 = 都有一块大屏，
  大屏展示**角色之间的协调交互**与**待处理的问题和决策**。大屏是本体，场景是皮肤
  ——同一块大屏换不同 dressing。
- **大屏两类核心内容（v1 卡族，数据源全既有）**：
  1. **协调交互流**：角色间投递（谁 → 谁说了什么，UPS 事件）、编排流转（run 进度、
     边触发、pending 谁身上）、化身状态变迁——多角色工作流的实时脉搏。
  2. **待办决策队列**：阻塞问答（`QuestionTracker`——AskUserQuestion / 权限确认）、
     待批战报（review 批阅）、旁路问题（`side_questions`）——**人要拍板的都在这**，
     大屏是「上帝视角的收件箱」。
- **大屏 = 可插拔展示位**（机制层）：展示卡注册表声明「kind → 派生数据源映射」，
  按场景配置摆哪些卡；**只摆有数据的块、没有就不摆、绝不摆空壳**（statusline 面的
  既有一贯哲学）；后期加新效果 = 注册表加一行卡，场景骨架不动。卡内容全走适配层
  读侧（派生面），大屏零新数据源。
- **视觉**：像素风 Q 版按 weaveRPG.md 第五章。
- **技术选型（2026-10-26 定稿）**：骨架/数据/路由/拓扑全复用既有栈（React 19 +
  Tailwind + TanStack Query + SSE 单通道 + route.ts + @xyflow/react——团队×任务
  俯视图复用编排画布同款）；状态机**不加框架**（纯函数映射，XState 被裁决排除）；
  渲染 v1 = CSS sprite + `image-rendering: pixelated` + CSS keyframes（零新依赖），
  RPG-3 视需要评估 PixiJS（渲染库非引擎）；**Phaser / Three.js / Zustand / Redux
  排除**。真关键路径是 sprite 资产链（CC0 包或 AI 生成）与像素中文字体子集化——
  资产工作量 > 代码。约束：伞包 tgz 自包含分发 ⇒ 新依赖高门槛；渲染库只准被
  `web/src/rpg/` 子树 import（零耦合裁决的依赖延伸）。

### 5.2 游戏语义层（动词门面，server 侧）

游戏视图的一切写操作**先抽象成游戏动词**，门面把动词翻译成既有 API 调用（用户裁决：
「例如安装技能接口，在游戏中需要抽象成修炼与经验成长，还有技巧维度的评分」）。
门面落 server（`/rpg/*` 路由 + game-verb service，内部调既有 service / API 逻辑），
**门面就是适配层（第一章裁决 6）的写侧**；web 只发游戏动词，**不拿游戏标签自拼
REST 调用**（否则游戏词汇散进 web，违反 web 只渲染）。

| 游戏动词 | 底层既有 API | 游戏事实（RPG 域表） |
|---|---|---|
| **修炼**（学技能） | 技能安装（market / install skill） | 成长记录 + **技巧维度评分** |
| 进阶 / 换装 | 插件 / MCP 安装（install） | 成长记录 |
| 组队 | 团队声明写（协调者仓库 `teams/`） | — |
| 出征 / 接任务 | 编排触发（trigger） | — |
| 传音 | 消息投递（`MessageDeliverer.send`） | — |
| 点卯 / 休整 | 会话创建 / 中断（既有面） | — |
| 批阅战报 | review 批阅动作（定位稿①） | — |

**技巧维度评分**（修炼的产出）：按七型维度（能量 / 思考 / 创造 / 连接 / 审核 /
执行 / 适配）出分——初始分 = 角色模板基线，后续分 = 修炼后实战表现派生（回合
成功率、任务完成、协作投递统计）回写。评分是游戏事实落 RPG 域表，但**计算素材
全派生**（不新采任何数据）。

**门面的边界**：一个动词 = 映射 + 组合（可一次串多个既有 API）+ 游戏事实记录，
三件事之外什么都不做——安装校验、路径归属、投递层序、编排闸全部留在既有 API。
后期可将动词面经 MCP 暴露（`weave-rpg` server），让协调者 / 外部 agent 也说游戏
词汇（缓做，随 MCP 生态计划评估）。

**红线**：游戏视图零新数据源（观察态全派生）、零新写实现（写操作全走动词门面 →
既有 API）。游戏视图只是「换一双眼睛、换一套词汇看与操作同一份真相」。

### 5.3 角色对象模型（本体-皮肤分离，2026-10-26 用户补充建模）

**核心分离：本体（RPG 语义域）⊥ 皮肤（场景呈现）**。武器 / 六维 / 装备是本体层的
对象与数据；「会议室里武器是笔记本型号、武林大会里武器是剑」是皮肤层对同一本体的
呈现映射。皮肤 = 资产包 + 映射表，**零数据、零逻辑、不是代码分支**——server 不知
皮肤存在，皮肤只落 `web/src/rpg/` 子树（零耦合裁决的延伸）。

#### 5.3.1 对象模型与属性（本体层）

| 对象 | weave 真身 | 层级 | 属性 |
|---|---|---|---|
| **角色（Role）** | 项目 | 角色级（项目档） | 名字、模板（七型 → 初始六维）、六维分值、技能集、装备库、XP/等级（派生）、团队归属 |
| **化身（Avatar）** | 会话 | 化身级（会话） | 当前武器（模型）、内力（上下文长度）、招式强度（effort 档位）、**负责模块**（同角色多实例的分工声明）、状态机、战斗记录（事件链） |
| **武器（Weapon）** | 模型 | 化身级 | 真名（模型名）、品阶（档位映射：haiku→凡铁 / sonnet→精铸 / opus→光剑，词表可配）、切换史（`modelFactEvents`） |
| **技能（Skill）** | skill 安装 | 角色级 | 六维加成声明（增强哪维、加多少）、来源（门派基础 = user 档继承 / 自修 = 项目档安装） |
| **装备（Equipment）** | plugin / MCP | 角色级 | 槽位（plugin 槽 / MCP 槽）、穿戴态（`ToolStateRow` 的 install + effective） |
| **门派基础** | user 档全局 skill | 全局 | 所有角色先天继承的功法（既有作用域机制） |
| **军师** | 决策模型 | 全局配置 | 修炼评分与任务判断的外援（settings `decision` 单源） |
| **分身术** | fork 子 Agent / worktree | 化身级 | 召唤帮手（fork）/ 平行空间修炼（worktree 绑定，P2 落地后） |

#### 5.3.2 六维词表与计算

维度封闭词表（v1 六维，用户定名）：**力量 / 智慧 / 敏捷 / 速度 / 内力 / 运气**。
与七型模板的关系：**七型是构造词汇（模板怎么拼），六维是成长词汇（长成什么样）**——
模板声明初始六维分布，Skill 声明加成，实战派生修正后置（RPG-3）。

```
六维分值 = 模板基线（七型 → 初始分布）
         + Σ 已装 Skill 加成（修炼记录）
         + 实战派生修正（RPG-3：回合成功率→运气、响应时长→敏捷、
           改动量→力量、决策参与→智慧、上下文利用→内力、吞吐→速度）
```

计算是适配层读侧的纯函数，素材全派生；分值快照随修炼落 RPG 域表（行动态）。

**七型 → 六维初始分布（简版占位，RPG-3 调参）**：每型总 18 点、主维 5、次维 4、
短板 2——

| 型 | 力量 | 智慧 | 敏捷 | 速度 | 内力 | 运气 |
|---|---|---|---|---|---|---|
| 能量 | 5 | 2 | 3 | 3 | 3 | 2 |
| 思考 | 2 | 5 | 2 | 3 | 4 | 2 |
| 创造 | 2 | 4 | 3 | 3 | 3 | 3 |
| 连接 | 2 | 3 | 4 | 3 | 2 | 4 |
| 审核 | 3 | 4 | 3 | 2 | 3 | 3 |
| 执行 | 4 | 2 | 3 | 5 | 3 | 1 |
| 适配 | 3 | 3 | 3 | 3 | 3 | 3 |

**XP / 等级公式（简版占位）**：XP 来源 = 任务完成（run done = 100 × playbook
难度标注）+ 有效回合（每回合 2）+ 首次修炼（每 skill 10）+ 协作（**留位**，卡在
11.1#3 数据源）；等级阈值 = `100 × level²`（L1→100、L2→400、L3→900）。数值全为
初版占位，跑起来后按真实分布调参。

#### 5.3.3 状态机（各对象，全部派生映射、无本地运行时）

| 对象 | 状态 | 来源 |
|---|---|---|
| 化身 | idle / 工作中 / 蓄力（compacting）/ 受伤（failed）/ 离场（terminated） | `deriveSessionStatus` 映射（既有） |
| 武器 | 装备中 / 切换中 | `modelFactEvents` 最后已知（既有）；无独立状态机 |
| 装备 | 已穿戴 / 已卸下 / 可穿戴 | `ToolStateRow` install + effective（既有） |
| 修炼 | 进行中 → 完成 / 失败 | 安装过程态（既有安装面） |
| 六维 | 纯数值，无状态机 | 派生计算 |

**不引入 XState**：所有状态都是既有 weave 状态的映射，没有需要本地推进的状态机
（任务状态机 = L2 编排 run，已有）。

#### 5.3.4 方法调用层次

```
web/src/rpg/（皮肤 + 视图，只发游戏动词 / 只收派生面）
  ↓ /rpg/* 动词门面（game-verb service：映射 + 组合 + 游戏事实记录）
  ↓ 适配层（RpgAdapter 接口，读侧 + 写侧）
  ↓ ┌ 读侧：既有派生面（会话状态 / modelFact / ToolStateRow / hook_events 统计）
    ├ 写侧：既有 API（技能安装 / 模型切换 / 插件启停 / 编排触发 / 消息投递）
    └ RPG 域：成长记录 + 六维快照 + 评分（行动态，唯一新表）
```

#### 5.3.5 皮肤层（场景主题）

- 皮肤 = **资产包（立绘 / 图标 / 音效可选）+ 呈现映射表**（本体 kind → 场景内
  呈现物与文案），按场景绑定：办公区俯视 = 默认主题（武器直显模型名 / 工作站）、
  教室 / 会议室 = 现代办公主题（武器 = 笔记本型号）、武林大会 = 江湖主题（武器 =
  剑：凡铁 / 精铸 / 光剑按品阶）。
- 映射表是声明式数据（皮肤包内 JSON），**加新场景 = 加一个皮肤包，本体与门面零
  改动**；品阶词表（模型档位 → 品阶名）归皮肤包自带。
- **分发与注册制**（2026-10-26 用户裁决）：皮肤包经**用户自定义安装的 weave 插件**
  分发；weave 提供**抽象接口（皮肤 manifest 约定）+ 内置 skill（教用户 / agent 生成
  皮肤包的开发指南与脚手架）**。加载 = **注册制：扫描到该插件的皮肤 manifest 即
  注册**（对齐插件系统既有发现机制；插件机制改动走三件套硬约束——PLUGIN-SPEC +
  内置仓 weave-plugin-creator skill + marketplace.json）。皮肤插件的 manifest 形态
  （目录约定、场景绑定声明、资产引用）列入待设计（11.3）。
- 皮肤不改变语义：换皮前后动词、六维、数据完全相同——「同一份真相，不同的眼睛」
  的最后一层。

#### 5.3.6 RPG 域表（简版 DDL，2026-10-26 起草）

```sql
-- 修炼/成长记录（行动态：动词门面写入）
CREATE TABLE IF NOT EXISTS rpg_growth (
  id     INTEGER PRIMARY KEY AUTOINCREMENT,
  role   INTEGER NOT NULL,       -- projects.id（级联删）
  verb   TEXT NOT NULL,          -- cultivate | equip | ...
  target TEXT NOT NULL,          -- skill / plugin 名
  detail TEXT,
  at     TEXT NOT NULL
);
-- 六维快照（修炼/修正后落，历史可回放成长曲线）
CREATE TABLE IF NOT EXISTS rpg_hexagram (
  role  INTEGER NOT NULL,
  dims  TEXT NOT NULL,           -- JSON {力量:5, 智慧:2, ...}
  reason TEXT,                   -- 触发来源（哪次修炼/修正）
  at    TEXT NOT NULL,
  PRIMARY KEY (role, at)
);
-- 技巧维度评分（修炼产出）
CREATE TABLE IF NOT EXISTS rpg_scores (
  id    INTEGER PRIMARY KEY AUTOINCREMENT,
  role  INTEGER NOT NULL,
  skill TEXT NOT NULL,
  score INTEGER NOT NULL,        -- 0-100
  basis TEXT,                    -- 判据摘要
  at    TEXT NOT NULL
);
```

化身分工（module）不落库：声明态在 teams 文件、运行态从编排节点绑定派生——
v1 不加化身分工表。修剪纪律对齐 `extension_executions`（每角色 200 条 + 7 天）。

## 六、mTCP 发现与跨机联邦

- **mTCP 发现（本地）**：mDNS / zeroconf 广播 daemon 的 MCP 端点（服务类型
  `_weave-mcp._tcp`，实例名带机器标识，TXT 记录带版本与 capabilities 摘要），LAN 内
  其他 weave / agent 客户端可发现并直连对端 MCP 面。发现服务只广播、不接收执行——
  安全面不变（对端仍要令牌）。**两级形态**：手动添加 `host:port` 是基础（D8 原文），
  mDNS 自动发现是增强——**发现到 ≠ 可用**，仍须 pairing。实现选型：Node 侧纯 JS 库
  （`bonjour-service` 一类，零原生依赖——伞包自包含分发约束排除 `mdns` 原生编译包）。
- **联邦（跨机）**：对齐 `session-orchestration.md` D8 预留，不另起炉灶——peer
  daemon 注册表（手动 `host:port` + pairing token；mDNS 自动发现为增强）、
  `MessageRouter`（目标会话不在本地 sessions → 查 peer 表 → 转发）、peer 握手互报
  `messaging/capabilities` 矩阵（远端支持状态同构呈现）。**安全红线照 D8 原文**：
  pairing 显式授权、联邦默认关闭、一期转发仅 inject 模式。
- **通信协议（2026-10-27 补定 + 2026-10-27 用户裁决：服务注册与路由）**：
  - **协议形状 = 服务注册与发现，调用方无切换感知**（用户裁决，替代「联邦专用端点
    vs 复用 API」的二选一）：一切跨机可能的服务调用统一走 **ServiceRegistry +
    ServiceRouter**——调用方给「服务名 + 语义参数」（既有惯例：server 只传语义参数、
    `HarnessRegistry` 注册制先例），路由层查注册表决定**本地直调或远程转发**；业务
    代码零 if-else，联邦落地时调用方零改动。**先例同源**：`HarnessRegistry` 就是
    注册制（harness 注册能力面），D8 的 MessageRouter 是本模式在消息投递一个场景
    上的特例——推广成通用路由层。
  - **注册粒度 = 两层**：能力级（peer 握手互报提供哪些服务——capabilities 互报的
    D8 语义变成注册表行）+ 资源级（角色/会话在哪台机器——teams 的 `peer:` 来源
    就是资源路由表）。路由先按资源查归属、再按能力查可达。
  - **副作用标注**：服务表每行标「只读查询 / 有副作用动作」——只读可自由路由远程；
    副作用类默认本地，联邦一期只放开投递类（对齐 D8 一期 inject-only，路由层不许
    变成任意远程执行通道）。
  - **门的形状 = 联邦专用端点（2026-10-27 裁决）**：`/federation/*` 段——`pair`
    （pairing 握手）/ `caps`（capabilities 互报 = 服务表外露行）/ `call`（服务调用
    `{service, params}`）/ `heartbeat`。整段只认 per-peer token（认证豁免段模式同
    `/webhooks`）。**默认拒绝**：外露面 = 注册表中「标外露」的服务行，不注册就不可
    远程触达——副作用标注与一期 inject-only 从「过滤规则」变成「表里没有」。**两端
    对称**：对端收到 `call` 后走自己的本地路由器直调既有 service——服务实现完全
    复用，专用的只是门（被否的「复用现有 API + token 过滤」方案：认证门无按凭据
    裁路由的维度、通用 API 暴露本机专属信息、白名单过滤是先全开再裁的漏裁模式）。
  - **路由层 = 可观测单点**：origin 标注（api-log `peer` 档唯一判据）、超时/重试、
    错误形状归一（「不可达」与「拒绝」可区分）全在路由层一处。
  - **落地时机 = 接口先行、本地先落**：路由器先全本地直调（薄接口 + 注册表 + 本地
    路由，无远程分支——不过早抽象），作为 **C3（RPG-1 适配层）的实现底座**——适配层
    写侧打在服务路由上而非直接打在既有 API 上；F1（联邦批）只加远程路由器与注册
    流程，调用方零改动。
  - **传输 = TLS，复用既有基建**：daemon 已有 HTTPS 双监听（`selfsigned` 自签 +
    `server.tlsPort`，dashboard 局域网远程访问在用）——联邦走 HTTPS，零新传输层。
  - **令牌分三层**：本机 `localToken`（本机 dashboard/CLI/MCP 用，**绝不跨机**——
    各机一份是既有实测）；pairing token（配对握手，人工显式确认时交换）；per-peer
    token（联邦会话凭据，每 peer 一份、可吊销）。
  - **证书互信 = TOFU 指纹**：自签证书在 pairing 时对齐指纹；**待定项**（11.3）：
    纯 LAN 信任域是否提供「HTTP + token」降级档，默认建议 HTTPS + TOFU。
- **与 MCP 生态计划的交汇**：被缓做的**外部 webhook 扇入在联邦下获得第一个真实
  集成方**——peer 间的机器投递走对端 webhook / MCP 入口，联邦落地时一并复活
  （接线清单已在 MCP 分析稿 §1.6 备档）。
- **跨机 RPG = 联网场景（multiplayer，2026-10-26 用户裁决）**：联邦机制就是「联网」
  ——协调者可经局域网协调**其他 weave 实例**，把其他 weave 中的角色**招募进当前
  团队**，实现**共同的办公室、教室、武林大会**：多台机器的角色同处一个场景、
  同一块大屏（协调交互流与待办决策跨机聚合，数据源 = 联邦会话同构呈现，D8 预留），
  类似现实中的**数字孪生**效果。teams 声明的角色引用需带来源（本地 / `peer:角色`），
  协调者的「招聘」范围随之扩到全网——RPG 是联邦的第一个应用场景，也是它的验收场。
- **加入单位 = 角色 + 用户（2026-10-27 用户裁决）**：跨机加入的不只是角色——**远端
  的协调者（用户）也随自己的角色一起加入**，成为共享场景的参与者（教学模式里教师
  与学生互入对方场景即此形态）。
- **邀请制 + AI 选角（2026-10-27 用户裁决）**：加入走**邀请制**——用户跨机邀请
  其他用户，受邀用户加入时，**由 AI 从其角色库挑选哪几个角色加入**：优先决策模型、
  其次大模型——即决策内核的批量判定形态（`judgeBatch` 逐角色判适配 / `evaluate`
  选角并给理由，L1 批 1 的内核直接服务于此，零新机制）。邀请 = pairing 的**用户级
  显式授权**形态，D8 安全红线（显式授权、默认关）不变。
- **全程 HITL（2026-10-27 用户裁决）**：**接受邀请由受邀用户手动决策**；**AI 选角
  结果须用户手动确认后生效**——**可选自动模式**（显式 opt-in 开关，默认手动；对齐
  「新挂起待答只提醒不自动弹框、作答入口恒为手动点」的既有口径）。确认的呈现位 =
  大屏待办决策队列（受邀方视角），提醒走既有三腿。
- **应用模式定位**（数字孪生的两个先例场景）：**在线教育（教学模式）**——教师 =
  协调者（上帝视角），学生 = 各机角色，教室场景的大屏 = 共同黑板（任务板 / 点名 /
  成长榜跨机可见）；**会议模式**——会议室场景的大屏 = 多机共享的批阅与决策面。
  这两个模式是「会话操作系统」对外叙事的现成素材（定位稿第四章取向 1 的延伸）。

## 七、可观测与操作溯源（2026-10-27 用户裁决）

**总纲：计划中所有链路必须有完整可观测。** 链路 = 触发 → 闸 → 决策 → 端点 → 投递
→ 回执，每一段都落可查的日志或事件，贯穿键随行（`runId` / `executionId` /
`bindingId`）——一次任务的全链可回放。

**域日志分工**（各管各的段，互不复制存储）：

| 段 | 落点 | 贯穿键 |
|---|---|---|
| 编排 run（任务状态机） | `orchestration_runs` + RunEvent（既有） | runId |
| L1 扩展点执行 | `extension_executions`（stage / source / detail，设计稿已定） | executionId / bindingId |
| RPG 动词（修炼/组队/选角…） | RPG 域三表（§5.3.6） | growthId / 角色 |
| HTTP 接口（web / MCP / webhook / peer） | api-log 每请求一行（既有） | **origin 列（新增，下条）** |

**api-log 补调用来源（origin 列）**——编排据此正确区分**用户操作与 agent 操作**：

- origin 词表：`user`（web / CLI 认证会话手动）/ `mcp`（MCP 工具调用——协调者与外部
  agent 都在此档）/ `webhook` / `peer`（联邦转发，P5）/ `cli`。
- 落法：MCP 转发层（`api()` fetch）与 webhook 入口带 `x-weave-origin` 头，api-log
  记列；进程内引擎调用（编排投递 / 扩展点扇出不过 HTTP）不进 api-log，归各自域日志
  的 `trigger` / `source` 字段（已在两份设计稿定形）。
- **「用户操作 vs agent 操作」的唯一编排判据** = 批 2a 的来源维度 + 诱导回合登记
  （单点咽喉）——api-log origin 是观测面补充，不做运行时判据（两处各司其职）。

**任务状态机看板**：所有任务（= 编排 run）的状态机流转通过看板体现——web 既有编排
运行视图的**看板化**（run 卡按状态分列 + 流转历史），数据零新增（runs 表全够）；
**只读呈现，不做任务实体**（竞品的任务卡是 CRUD，weave 的看板是 run 状态机的镜子
——不做第二任务引擎红线）。

**统一编排视图（思维导图从左往右）**：编排总览新增 **LR 自动布局模式**——按拓扑
分层从左往右展开，节点带状态与进度（run 活跃 flash、pending 标记、边条件标注），
整体依赖与进度一眼可见；布局 = **自写纯函数分层算法**（拓扑分列 x、层内排 y——编排
图规模小，零新依赖，不引 dagre/elkjs）。画布编辑面（自由拖拽）不动——LR 视图是
总览的增强形态。

**RPG 游戏视角的看板与有向图**：RPG 内**单独**的游戏视角看板（任务状态机的游戏化
呈现）+ **游戏视角有向图**（同一 LR 布局纯函数 + 像素皮肤，依赖与进度同形态）——
本体同源（runs / 编排图），呈现两皮（仪表盘视图 / 游戏视图），与本体-皮肤分离
裁决一致。大屏的「协调交互流」卡（§5.1）就是这两者在共享场景里的聚合位。

| 级 | 工作线 | 理由 |

## 十、不做什么与红线

- **不做任务卡实体**：看板与任务栏都是编排 run 状态机的**只读呈现**，不出现可增删改
  的任务卡 CRUD（不做第二任务引擎的呈现面延伸——竞品的任务板在 weave = 编排图 +
  runs，已经存在）。

- **不做第二游戏状态源**：一切游戏态从既有数据派生（第一章裁决 1）；发现需要新落
  的事实，先问「这是游戏的事实还是会话的事实」——是后者的去扩会话域，是前者的
  才准进 RPG 域。
- **不做第二任务引擎**：任务 = L2 编排 run（用户裁决）；weaveRPG.md 的任务属性
  （难度/风险/奖励）是编排与角色的**标注**，不是新运行时。
- **不做游戏内写实现**：写操作全走动词门面 → 既有 API（第五章 5.2）；门面永不自带
  业务裁决。
- **RPG 与既有代码零耦合**：一切交互经适配层（第一章裁决 6），既有域不出现游戏
  词汇、不 import RPG 模块；适配层接口是唯一接触面，改 RPG 不动既有域、改既有域
  只动适配层实现。
- **角色仓库不绕过 init 写策略**：`.weave/` 可覆写、用户文件只追加合并。
- **联邦安全红线照 D8**：pairing 显式授权、默认关闭、一期 inject-only；mDNS 只发现
  不授权。
- **v1 不做多实例角色**（转生 / 分身）、不做 RPG 专属 SSE 通道（复用既有帧域）。
