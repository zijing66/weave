CLAUDE.md 只保留当前站立规则；带日期的定案、实测记录、用户原话裁决与被推翻的旧结论一律记录在这里。append-only，新的在上。

## 2026-10-16

- **对话气泡的触屏手势：双击开右键菜单，长按不再直达多选（用户原话直投「移动端，会话改成双击出现右键菜单，而不是长按直接多选；只有桌面端是右键打开右键菜单」）**：推翻的是同日「移动端所有右键面一律配长按等价」里**对话弹窗那一路的手势**（该条站立规则收成「默认长按等价 + 对话弹窗例外走双击」，账本见 CLAUDE.md 移动端条第 ⑥ 项）——气泡上触屏长按不再进多选，改为**双击开桌面右键那一份菜单**（多选只是菜单里那一项），桌面端维持只有右键开菜单。**判据**：同一条气泡、两击间隔 ≤300ms、位移 >8px 即取消（沿用长按那套 slop，不夺滚动/拖拽），仍只在 `(pointer: coarse)` 下挂、`onContextMenu` 照旧只 `preventDefault` 压原生菜单；菜单照旧夹在视口内。**坑：移动浏览器的双击缩放会抢手势**——气泡行挂 `touch-manipulation`（`touch-action: manipulation`，pan/pinch 不受影响）压掉它。**顺带删掉「吞掉长按后补发的 click」那套**（`suppressTap` + 卸载清 timer）：双击的两击都落在非多选态（那时 `onClick` 本就 undefined，只有多选态点气泡才勾选），补发 click 无害；菜单外关闭本就走 `pointerdown`，不受 click 干扰。**`ProjectList` 不动**：项目行仍是长按等价（用户只点名「会话」）。
- **层② 文本通道与「开窗 preset」解耦（peer 会话转达用户报：「还有已打开wezterm时，然后切换设置的终端为Windows terminal，此时，发送停止按钮是 停止失败：Interrupting needs a text-capable terminal (pick wezterm in settings)」）**：**机制**——`opener.ts` 的 `promptTerminalChannel` 把层② 的**全部**能力（`available` / `listPanes` / `locatePane` / `locateScreens` / `sendText` / `sendKeys`）都从 `settings.terminal` 取后端，但 `settings.terminal` 答的是「weave 该往哪个终端开窗」，层② 的作用对象却是**已经跑的会话所在的 pane**——其归属凭据是 hook 旁路上报的 pane env（`WEZTERM_PANE`/`WEZTERM_UNIX_SOCKET`，`MessageDeliverer.notePaneEnv` 存内存）。两者只在用户从不改 preset 时重合：preset 换成 `wt`（或 win32 缺省 `auto`，`AutoBackend` 的文本位同样是 false）后 `terminalChannel()` 恒 null ⇒ `sessionKeysTarget` 在最前面就 409，`locatePane(env)` 根本没机会跑；`locateScreens` 被同一个开关挡着返回 `{}` ⇒ 会话列表的同屏分块一并静默消失。**修法 = 按 pane 证据分两处取后端**：`available`/`locatePane`/`locateScreens`/`sendText`/`sendKeys` 走 `paneBackend()`（配置的后端能打字就用它，否则回落 wezterm 后端——全仓唯一实现文本通道的后端，pane env 的解析与 pane id 的表示法也都出自它）；**只有标题+cwd 启发式回落的枚举面 `listPanes` 仍走配置的后端**（不跨世界猜——否则 macOS `terminal` preset 的用户会因为恰好有 wezterm 而被误 ESC）。**顺带**：`WeztermBackend.locatePane` 把「两个定位键缺一即不是 wezterm 会话」的判据挪到枚举**之前**（与 `weztermPaneFromEnv` 同一条件，只是省一轮 spawn；非 wezterm 项目的每次定位不再空枚举 mux，测试也就不再真 spawn）。**409 文案**：web 是 `'tasks.stopFail': '停止失败：{error}'` 直拼，故两条 409 改成中文修法（「找不到会话所在的终端窗口（只有 wezterm 里的会话能被远程击键）」/「终端通道未装配，无法远程击键」），`sessionKeysTarget` 的 `what` 参数随之删除。**被否掉的方案**：只在 control（停止/作答）面解耦、保留投递面 —— `terminalChannel()` 这一个闸有四处消费者（能力矩阵 / 诊断 / 层② 投递 / 击键），只改一处等于「按钮能亮但消息照样投不走」，语义不成立。**影响面**：纯 daemon 侧，项目生成物无需重跑 `weave init`。

- **跨会话消息错投事故：inbox 直投凭据被按组聚合（用户报「在 A 会话里发的消息跑到了 B 会话」）**：**机制**——hook-handler 的 inbox 分片按**项目 token** 切片（认 token 不认会话），消费侧 `drainClaim` 按 token 分组后，把 `messaging`（inbox socket 直投凭据 = 会话级事实）当成组级字段「取组内最后一个」，再对组内**每条**记录调 `noteInboxSocket(记录的 sessionId, 组级凭据)` ⇒ 同项目两个会话在同一 200ms 认领窗里都有事件时，整批会话的凭据全被写成「最后那行所属会话」的 socket；此后对另一个会话发的消息照这个映射直投，就落进了它的邻居。**为什么是间歇的**：每 tick 覆盖写一次，谁的行最后落在 claim 里就归谁——同项目两个会话都在刷工具事件时，等于每 200ms 重新掷一次币，于是表现为「有时对、有时错」。**取证**：接收方转录里那条 UPS 带 `[weave] ` 前缀（来源标记**只加在直投这一条路径**：终端 send-text 是裸文本、中继带 CC 的 `<cross-session-message>` 壳、注入走 additionalContext），且 promptbox 三个分片全空（= 投递侧记的成功，不是三层回落）⇒ 定位到直投凭据错配，而非 pane 回落打错窗口。**修法**：`messaging` 改为与 `inputs` 逐行对齐（同 `terminals` 早就采取的口径），并补回归测试「同批两会话各拿自己的 socket、未上报的那行 null」。**教训**：分片键（项目）与事实的作用域（会话）不是一回事——会话级旁路事实必须逐行携带，别信「一条 claim = 一个 hook 进程 = 一个会话」的直觉；同一份数据里 `terminals` 已经按逐行写、`messaging` 却按组写，正是这个直觉漏掉的一半。**波及面**：纯 daemon 侧缺陷，项目侧生成物（hook-handler.cjs）无需重跑 `weave init`，升级 weave 本身即修。
- **会话建档判据反转：会话行随首个事件即建（用户原话经 peer 会话转达「当前是否有会话只有有消息后，才显示在列表的逻辑，现在要求应该是，新建会话，就应当马上出现在会话列表，如果没有额外的 prompt 会话消息，超时后才删除，并且会话列表要显示会话剩余的保留时间」）**：**被推翻的旧结论**——消费侧 `inbox-worker` 曾有 `needsSessionRow` 判据，只带 SessionStart 的会话不建档（当时的动机是「开了就 /resume 走掉的空会话别在列表里留残影」），代价是新建会话要等到**首条 prompt（或闲置 Notification）**才现形——用户看到的正是这个空窗。**新规则**：`insertBatch` 对每个首次出现的 sessionId 无条件 `hookSessions.touch`，不按事件类型挑拣；残影问题改由既有幽灵期限收拾（`autoDeleteAt` = lastSeenAt + 10 分钟，收到过 UserPromptSubmit 即 null，「超时后才删除」+「行内倒计时 = 剩余保留时间」两条本来就都在，只差建行这一环）。副作用（接受）：SessionStart 单例现在真的会**短暂出现又消失**，列表里「闪一下」是新规则的本意，不是 bug。与「三处开终端按钮 loading 挂到已进入」是同一根需求的两半——新建会话按钮等的「新会话行落进列表」在旧判据下要等到 prompt 才可能命中，故加载窗必须先有这一行才谈得上收圈（`createAwaitGate` 那把闸的 `new:<projectId>` 键靠它）。
- **wezterm-mux-server 泄露复盘（用户：「检查是否有 wezterm-mux-server 泄露的问题，没有及时清理」）**：确认泄露——实机 16 个 `wezterm-mux-server.exe` 常驻（10-12 23:09 → 10-16 18:19，全部父进程已死、无一被清理）。**机制（对照实验实测）**：`wezterm cli` 对**存在但无主/不存在**的 socket 路径缺省会「连不上就原地拉起 `wezterm-mux-server --daemonize`」——该进程永不退出，且 daemonize 子进程**继承调用方 stdio 管道**把探活挂到超时（当年 SocketProbeGate 注释里「探活 >250s 不返回」的真身）；对着已绑幽灵的路径再探则 rc=0 返回空世界 = 假成功。**weave 侧的触发面**：`weztermSocketCandidates` 的 pid 探活只查「号在不在」不查「是不是 wezterm」——陈旧 `gui-sock-<pid>` 文件不消失（wezterm 退出不清理）+ Windows pid 复用 ⇒ 死文件间歇性混进候选；preset=wezterm 且 dashboard 有 SSE 客户端时探活每 30s 一轮（`TerminalTopologyRefresher`），另有 `weztermLiveMuxesCached` 10s 缓存过期后的后台对账；**测试套件也真探**（vitest 全量跑的启动瞬间实测又泄一个）。**修复 = `weztermCli` 恒带 `--no-auto-start`**（官方开关：连不上直接干净 rc≠0；实测活 socket 行为不变、失联/缺失路径 rc=1 零 spawn）——`probeGate` 据此判永久死，从此探陈旧文件只是浪费一次 spawn、不再是泄进程；arg 塑形抽 `weztermCliArgs` 纯函数入测试。**修不掉的残留面**（接受）：a) 别人手跑裸 `wezterm cli`（无 env → 默认 `sock`）仍会泄——weave 管不到用户手指，`sock` 已从候选里永久排除；b) `--no-auto-start` 后「socket 已死」是**永久**判死（同路径复用同 pid 的新 GUI 会被漏）——原行为更糟（幽灵假活），接受。**一次性清理**：杀 16+2 个幽灵（含对照实验自产的）、删 8 个死 pid 的 `gui-sock-*` 与裸 `sock`（`net.connect`/`.NET` 在 Windows 上连不了 AF_UNIX，纯 Node 无害预检不可行——这条也堵死了「预检代替 flag」的方案）；幽灵进程不解绑就杀不损失任何东西（实测全部绑在已删/不存在的路径上，域内无 pane）。**不做的事**：不加「自动清幽灵」——分不清「weave 泄的」与「用户故意跑的 headless mux」，杀了别人的服务不好交代；诊断面（doctor 报存量幽灵）留待需要再说。
- **三处「开终端」按钮的 loading 统一挂到「已进入」（用户原话经 peer 会话转达：「注意多处打开终端的按钮，loading要保持一致，需要进入对应的会话或者终端后，才能够结束loading状态，目前新建会话的按钮有问题」）**：原先只有**会话行**那枚是对的（loading 挂到该会话 `pidAlive` 转绿，30s 兜底），项目行「打开终端」与表头「新建会话」都是 **POST 一返回就收圈**——而两条路都是 detached spawn（新窗/tab 起来要秒级、claude 再发 SessionStart 才落行），空窗里按钮已经转回静止，用户看不出有没有生效、会再点一次（fb 的吞连点只挡得住 loading 期间那一下）。**三个判据各不相同，因为落点各不相同**：会话行 = 该会话 `pidAlive`（绿即已开——这一条早就是对的）；项目行 = **该项目终端角标上涨**（`terminalTopology` push 的 `counts[projectId]`，服务端 600ms 后自对账那一拍，上限取 8s——角标口径只在可枚举的终端后端上成立，探不到就照旧提前收圈，别把按钮钉在转圈上）；新建会话 = **新会话行落进列表**（POST 前快照已有 sessionId 集合，出现集合外的行即命中）。**为什么新建会话不能等「转绿」**：全新会话的第一条事件是 SessionStart，而 SessionStart 单例行的存活三态恒 `null`（见 `pidAliveOf`：无 prompt 的空壳行不判活）⇒ 等转绿会一直等到超时；等「行入列表」才是「确实进去了」在客户端能观测到的等价物。**抽象落点**：`web/src/lib/await-gate.ts` 的 `createAwaitGate(timeoutMs)`（key + `hit()` 判据、数据变 `poke`、命中或超时放行、卸载 `releaseAll`）——原先会话行那段 `aliveWaiters` 手写 Map 收编进它，三处共用一把闸；**刻意不做轮询也不做订阅**（判据由调用方给，闸不需要懂会话行或角标长什么样）。落地 = `TasksPanel`（会话行 / 新建会话，30s）+ `App`（项目行，8s）。
- **消息投递诊断面（用户原话「帮我核对，什么情况才会缺失，然后给api补充一些本地诊断的入口，诊断能够覆盖类似的所有问题」；两条 AskUserQuestion 裁决）**：起因 = 同事一台 VDI 上「发消息一直显示排队中」——远程查下来**三层通道结构性全死**（项目侧采集脚本生成于「上报凭据」之前 ⇒ 无直投凭据；终端 preset 是 wt（无文本注入后端）⇒ 层② 缺位；宿主注册表里那条会话没有 peer name ⇒ 中继也跳过），于是每条消息都落 promptbox 成 `pending`，队列永远没人取。**关键结论：这不是版本旧、不是重装能修的**——`weave daemon` 起的服务与前端早就新了，缺的是**项目侧生成物**：`.claude/helpers/hook-handler.cjs` 的重写判据是文件里含 `@version weave@` 这一子串（与版本号无关），所以**重跑一次 `weave init`** 就会刷成新脚本（存量项目每条 hook 采集开关同此代价），再重启会话即恢复直投；重发包本身**修不了**那台机器。**两条裁决**：① 出口面 = **API + 扩 `weave doctor`**（不做 web 面板——这类问题发生在「服务装上了、但本机接线不对」，要的是能对着终端读的一屏）；② 口径 = **被动只读**（不真连 socket、不枚举 pane、不起中继——那会真起子进程并可能改变状态）。**落地**：`CaptureSurface.scriptHealth`（harness 探针：脚本档位 user/project/none、是否 weave 生成、生成版本、`reportsInbox` / `reportsPaneEnv` 两个能力位，**只读文本不执行**）→ `MessageDeliverer.diagnose`（每会话三通道各自 `ready|unavailable|unknown` + 原因码、队列条数、暂停闸、存活三态）→ `GET /messaging/diagnostics`（`?session=` / `?project=` 可选；**凭据本身——socket 路径与 token——永不进响应**，只出「有没有」）→ `weave doctor` 增一节人类可读版（提示码 → 中文修法）。**为什么单起一条只读端点而不是把字段塞进 `/sessions`**：诊断要跨「采集脚本 × 会话 × 队列 × 暂停闸」四个面，塞进列表接口等于每条列表都付这份推导；而且诊断天然是**按需**看的。**为什么提示码要在 server 拼**：web/CLI 都不该知道「哪种原因对应什么修法」，码表与文案各在 i18n 一处。
- **`openDatabase` 的 `busy_timeout` 必须排在 WAL pragma 之前（实测事故：自测时把本机 daemon 打挂）**：现场 = `weave daemon stop` 后立刻 `daemon start`，紧接着一条 CLI 命令报 `disk I/O error`（`db.ts:156` 的 `PRAGMA journal_mode = WAL`），新起的 daemon 一起死。真因 = **顺序**：`busy_timeout` 原先写在 WAL pragma 之后，于是那条独占写（改数据库头）落在 `busy_timeout=0` 的窗口里——daemon 正在启动（跑 SCHEMA + 三条迁移 = 持写锁）时另起的 CLI 撞上它**无重试**，Windows 上直接报成 `disk I/O error`（SQLITE_IOERR）而非 BUSY。修法 = 把 `busy_timeout` 提到最前（两行搬家，与既有注释「默认 0 会让瞬时争用直接抛 SQLITE_BUSY」的意图一致）。**附带实测**：daemon 冷启动到 `/health` 可用约 **17 秒**（500 MB 级库 + 迁移 + 重建内存态），而 `daemon start` 是 `spawn(detached)` 后立刻返回 ⇒ **启动后不要抢在它前面开库**（脚本/CI 里先探 `/health` 再干别的）。`weave.db` 的 `-wal` / `-shm` 会随 checkpoint 出现又消失、`page_count` 稳定，别据此判损坏。
- **前端数据层 = 总线发布订阅 + TanStack Query 增量并入（用户裁决「总线 + TanStack Query 增量上」）**：起因 = 用户问「前端各组件是否可以改成从总线进行发布订阅制，架构更加清晰。除非是页面特定的独立sse接口」，中途又问「是不是利用成熟的 react 框架重构前端，成本会更低？」。裁决路径 = 把前端数据问题拆三层看：① SSE 分发——EventSource 只有一条、分发逻辑任何框架都不会替你写，**手写躲不掉**；② 拉取/缓存/失效——TanStack Query 与既有 fetcher/invalidate 形态 **1:1 对应**（`invalidate` 帧 → `invalidateQueries`），这是框架真正付钱的地方；③ 状态容器——本仓痛点不在-redux。⇒ 组合路线，不整仓换框架。**第一部分（总线发布订阅，随 `be2921b` 落地——那次提交是并行会话的，我的暂存被共享索引卷入，按纪律接受归因噪声）**：`lib/sse.ts` 单一 EventSource 不变，分发拆四个订阅面——`subscribeFrame`（按帧类型）/ `subscribePush`（按载荷 key）/ `subscribeHook`（按 kind，支持 `message.` 尾点前缀）/ `registerInvalidator`（失效域，一 key 多注册者）——拆除两层旧转发：App 的巨型 switch 与 `window` `weave:hook` CustomEvent 转发（7 个组件各订各的 kind）；`weave:rules-changed` 是本地 UI 事件不是 SSE，**保留 window 事件不动**。App 的 toast 顺手修掉一个 stale closure（旧依赖漏了 `allSessions`，toast 一直用挂载时的会话表）。**第二部分（`6e0fc5c`，projects 域试点）**：`main.tsx` 装 QueryClientProvider，全局缺省 `staleTime: Infinity` + `refetchOnWindowFocus: false` + `retry: false`——**刷新只走 SSE 信号**是本仓语义（事件驱动、不轮询），Query 的活跃窗口语义必须显式关掉；projects 查询单独覆写 `refetchOnWindowFocus: 'always'` 保留既有可见性重拉口径（daemon 对账 ≤5s 窗），手工 `visibilitychange` 监听删除。桥接范式 = `refreshProjects` 改为 `invalidateQueries(['projects'])`，SSE 的 `subscribeFrame('project')` / `registerInvalidator('projects')` 原样喂它——**今后每个域照此并入、不抢跑**。骨架门 = `isPending`、初载失败才报错（`isError && data === undefined`，静默刷新失败不变）、拖拽排序改 `setQueryData` 乐观更新 + 失效回滚。例外确认保留：AI 助手的 fetch-reader 流式是页面专属独立流（EventSource 只支持 GET），不经总线。
